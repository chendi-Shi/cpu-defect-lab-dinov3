# CPU Defect Lab：做了什么、怎么做、问题如何解决

后续已完成一轮螺丝漏检改进，完整方法、实际结果、问题和失败案例见[螺丝改进报告](SCREW_REFINEMENT.md)及[面试解释](SCREW_REFINEMENT_INTERVIEW.md)。下文保留初始四类别实验的历史记录；新的336方案仅在螺丝专用入口提供。

这个项目把近期工业异常检测论文的核心方法，变成了可以在普通笔记本上复现、评估和演示的完整实验。硬件是 Intel i5-1130G7、约 16 GB 内存，没有 NVIDIA 显卡。全程使用 CPU；没有从零训练、微调 DINOv3，也没有 GPU 训练经历。

方法来自 [DINOSaur（ECCV 2026）论文](https://arxiv.org/abs/2605.24251v2)及其[官方代码固定版本](https://github.com/Continue-Edge-AI-Lab/Rethinking-Continual-AD/tree/9574f14f2e5a99e605ed19f0ff78f0a496d29252)，骨干使用公开的 [DINOv3 ViT-S/16 权重](https://huggingface.co/timm/vit_small_patch16_dinov3.lvd1689m)。项目贡献是独立实现核心检索、CPU 适配、控制变量实验、错误分析与工程验证。DINOSaur 算法和 DINOv3 预训练模型属于原作者；本项目不是原创这两个方法，也不是完整论文 benchmark 或全球 SOTA 证明。

## 1. 做了什么

项目处理 MVTec AD 中瓶口、螺丝、榛子、金属螺母四类工业图片，输出异常分数、固定阈值判断和异常定位热力图。建库只使用正常图片，测试缺陷标注只用于评估。

先实现 ResNet18 局部正常特征匹配基线，再以冻结 DINOv3 和 DINOSaur 空间特征库重做。完整评估包括四类共 24 次正式运行：主方法每类运行三个 coreset 种子，三组消融每类各运行一次。此外完成类别依次加入的路由实验、命令行推理、本机网页演示和固定 14 张图片试用。

| 类别 | 测试图数 | ResNet18 图像 AUROC | DINOv3 主方案图像 AUROC，均值±标准差 | 发布模型漏检／异常数 | 发布模型误报／正常数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| bottle | 83 | 0.9976 | 1.0000 ± 0.0000 | 0/63 | 0/20 |
| screw | 160 | 0.5190 | 0.7870 ± 0.0148 | 59/119 | 5/41 |
| hazelnut | 110 | 0.9350 | 0.9910 ± 0.0033 | 5/70 | 1/40 |
| metal_nut | 115 | 0.8827 | 0.9966 ± 0.0005 | 1/93 | 2/22 |

新主方法使用 coreset seeds 42、43、44，网页及 CLI 固定发布 seed 42。三个种子使用相同数据划分和测试集；标准差表示建库随机性的影响，不是独立测试集上的置信区间。四类图像 AUROC 都提高，但这不等于所有缺陷都能检出。尤其螺丝发布模型的召回率只有 60/119，即 50.42%。完整数值和逐缺陷混淆矩阵见[正式报告](FRONTIER.md)。

## 2. 怎么做

### 从图片到正常特征库

1. 固定数据及权重来源、版本与 SHA256。正常训练图按 split seed 42 分成 80% 建库、20% 独立正常校准，官方测试划分保持不变。
2. 将 RGB 图片以张量双线性方式 resize 到 224×224，启用 antialias，再转换 float32 并使用 ImageNet 归一化。
3. 冻结 DINOv3 ViT-S/16，通过 timm 提取最终 LayerNorm 特征：一个 384 维 CLS 向量和 14×14×384 的局部 patch 特征。移除四个 register token；不再作额外 L2 归一化。
4. 每个空间位置分别执行 greedy k-center，从正常特征中保留有覆盖性的代表。每个位置保留 `min(N, max(20, floor(0.1*N)))` 个向量，其中 N 是建库图片数。
5. 对测试图片的每个 patch，只在半径 3 的有效空间邻域查找最近正常特征，以欧式距离衡量异常程度。最大 patch 距离作为图像分数，patch 分数插值为 224×224 热力图。
6. 使用保留正常校准图分数的 95% 分位数确定阈值；测试图片不参与阈值选择。

算法实现见 [frontier_core.py](../frontier_core.py)，骨干适配、数据划分与正式运行见 [frontier.py](../frontier.py)。输入、库采样、特征归一化和论文偏离在[实验协议](../FRONTIER_PROTOCOL.md)中明确固定。

### 用消融检查组件，而不只看最终高分

主方法之外，分别替换成同预算随机采样、相同 k-center 库的全局检索、半径 0 的同位置检索。三组消融均使用 seed 42，其余数据划分保持一致。螺丝图像 AUROC 分别为主方法 0.7963、随机采样 0.7003、全局检索 0.7914、半径 0 检索 0.7010。结果说明本次设置下同位置限制过强，邻域和覆盖性采样值得保留；每组消融只有一次采样，不能据此宣称普遍最优。

榛子的全局检索为 0.9954，高于该类 seed 42 主方法的 0.9929。项目仍保留预先固定的主方法，没有根据测试结果更换每类最佳方案。旧版与新版同时改变骨干、特征维度和库构成，因此整套方法的提升不能全部归因于空间检索；解释组件作用需要看同一 DINOv3 流程内的消融。

### 加类别和做成可使用的演示

类别按 bottle → screw → hazelnut → metal_nut 加入正常库。每类正常建库图片的 CLS 均值形成原型，推理时用最近原型选择类别，再使用该类的特征库和阈值。每阶段重新检查已知类别路由，并重新计算已有库的内容哈希。

第四阶段共 468 张测试图的路由全部正确，已有库哈希不变，本次序列的旧类别指标未下降。这个结果只适用于四个已知类别、固定加入顺序和同一测试集；新增原型在其他数据上仍可能改变旧图片的路由。自动模式不会拒绝未知类别，不能称为通用物体识别或未知产品检测。

网页、CLI 与验收共用 `demo_server.Engine` 推理流程。网页可选四个新版类别、自动路由和两个旧版基线，支持真实图片上传，同时展示使用类别、分数、阈值、热力图和实际推理计时。报告保留每次运行的配置、逐图预测表、汇总、文件哈希及失败图，便于重新核算而不是只依赖截图。

## 3. 遇到什么问题，怎么解决

### 问题一：只有 CPU，最近邻检索容易占用过多内存和计算资源

把所有 query、正常库和 384 维特征同时广播为差分张量，会产生大规模中间结果。实现将空间检索拆成每次 8 个 query；全局检索同时拆分 query 和 reference，按 32 MiB 差分临时张量目标预算控制参考块大小。建库也按空间位置分块。32 MiB 是一个中间张量的目标预算，不是整个进程内存上限。

正式实验前以固定随机特征进行微基准，单线程组直接差分的一次观察值为 968.69 ms，禁用矩阵乘法的 `torch.cdist` 为 3719.28 ms。最终采用直接欧式范数、PyTorch 1 计算线程、骨干 batch=2，并缓存冻结骨干特征，让多种子和消融复用相同特征。微基准各设置只计时一次且后台负载不同，不能把它写成可靠的速度提升倍数。完整记录见 [RESOURCE_PROFILE.md](frontier/RESOURCE_PROFILE.md)。

### 问题二：看似更快的距离公式产生了数值误差

强制矩阵乘法的 `cdist` 在 float32 下出现相消误差：微基准中向量与自身匹配仍得到最高 0.00956832 的非零距离。最终保留分块直接差分＋欧式范数，避免这个公式带来的自匹配偏移。独立朴素循环参考与分块结果逐一比对，单元测试覆盖零自匹配、不同块大小和边角邻域。

邻域边界还有一个实现陷阱：把图片外的位置填成零特征，可能制造不存在的正常参考。代码显式标记有效坐标，把无效候选距离设为无穷，测试用非零正常库验证图片外位置不会产生虚假的零距离。

### 问题三：小样本和重复向量可能让 k-center 重复选点

直接沿用“至少 20 个代表”的逻辑，在不足 20 张正常图时无法选出 20 个不同索引；所有向量相同时，距离并列也可能重复选择同一点。实现将预算上限限制为 N，并维护已选索引掩码，每次仅在未选点中取最远点。测试覆盖 7 张图的小样本、37 张完全相同向量、种子可重复性和逐步最远优先性质。这个处理支持小样本运行，并不代表少量正常图片已足够覆盖实际产品变化。

### 问题四：论文、说明和骨干接口之间有细节差异

官方核心源码使用最终 LayerNorm 特征，而 README 的可选 timm 示例有额外 L2 建议；本项目按核心源码取特征，并在协议中披露选择。timm 输出包含一个 CLS、四个 register 与 196 个 patch，代码显式检查 token 数和 384 维形状，防止切错 token。RoPE periods 按模型卡建议先截断到 bf16 再回到 float32。

权重固定 revision 并核对完整 SHA256，运行库版本和预处理标识进入缓存身份。缓存 key 同时包含图片相对路径、实际文件内容、batch 和线程数；改变输入或特征实现会生成不同缓存。这些措施减少了错误加载和复用旧特征的风险，但 timm 替代仍属于适配，没有证明与 Meta 原运行库逐位相同。

### 问题五：高 AUROC 可能掩盖漏检，测试集也容易被用于调参数

设计上把建库正常图与阈值校准正常图分开，并让报告核查划分互斥、测试文件完全一致。主方法、参数和发布 seed 在正式评估前固定，保留所有类别和消融结果。对 24 次运行，用独立“异常图分数高于正常图分数”的两两比较算法重新计算图像 AUROC，与汇总记录的差值全部为 0。

报告同时呈现 TP、FP、FN、TN、F1 和每种缺陷漏检，而不只写 AUROC。例如螺丝 `scratch_head` 仍漏检 18/24，`thread_side` 仍漏检 17/23。瓶口和螺丝测试集在旧版中已查看过，因此它们属于探索性复测；新协议不能抹掉这一事实。像素 AUROC 在 224 网格计算，也没有包装成原图尺度官方指标。

### 问题六：离线成绩、发布模型和网页行为可能不一致

发布固定 seed 42 的四类模型，通过 manifest 校验模型哈希、骨干哈希、输入尺寸、特征维度、采样方案及有限数值。中断恢复只在配置相同且五个必要产物齐全时接受“已完成”；重算前清除旧汇总标记，新汇总采用临时文件写完后替换，避免不完整实验被误判完成。

验收启动真实本机 HTTP 服务，逐类测试正常和缺陷图片、手动模型与自动路由，共 16 次推理。先核对示例图片像素与离线输入一致，再比较得分、阈值和判断；八次手动类别推理的线上离线分数差值全部为 0。实际浏览器还验证了上传文件、模型切换清空旧结果、检测按钮状态、类别文字和热力图显示；浏览器错误日志为空。详见 [自动验收](FRONTIER_QA.json)与[浏览器验收](FRONTIER_BROWSER_QA.json)。

## 4. 哪些问题仍未解决

- **螺丝漏检仍明显。** 发布模型漏检 59/119 个异常，尤其细小划痕和部分螺纹异常。旋转、尺度、缺陷尺寸和空间匹配可能有关，但现有错误表不足以证明原因。下一轮应预先设计独立验证集上的分辨率、对齐或多尺度实验；不应根据当前测试集选择最有利阈值再报告。
- **未知类别与场景迁移没有解决。** 两张 Wikimedia 普通瓶子照片的距离很高，只能说明它们偏离工业正常库，不能声称准确识别了瓶子破损。14 张试用中的 12 张域内图全部判对，仍只是既有测试集样例展示，不是独立泛化验证。
- **性能和部署结论有限。** 缓存评分、特征提取和网页推理是不同计时范围；库大小不是进程峰值内存。历史基线和新版线程、后台负载不同，没有公平端到端速度对照，更没有生产现场稳定性测试。
- **复现覆盖有限。** 只覆盖四类 MVTec AD、224 输入、held-out 正常 95% 阈值和类别加入序列。没有覆盖原论文完整类别、97.5% 训练阈值、连续漂移、逻辑异常和边缘 GPU benchmark。

## 5. 面试时如何讲清项目价值

可以按“约束 → 方法 → 实验 → 验证 → 失败”展开：在无 NVIDIA 显卡的笔记本上，以冻结视觉骨干建立正常特征库；用同预算采样与邻域消融研究方法；通过独立指标核算与在线离线一致性验证结果；最终保留螺丝漏检和场景外输入，说明模型适用边界。

简历可使用的事实表述：

> 基于 DINOSaur／DINOv3 完成 CPU 工业异常检测复现与演示，在 MVTec AD 四类别完成 24 次正式运行、多种子与三组消融；螺丝图像 AUROC 由 ResNet18 基线 0.5190 提升到 0.7870±0.0148；实现分块特征检索、正常校准阈值、类别增量路由，以及 24 项单元测试和在线离线一致性验证。

项目由 AI 编程助手参与实现、实验与文档整理；代码贡献归属不能自动转换成求职者亲手完成的经历。用于简历和面试前，应亲自复跑并能解释上述算法、协议、失败与关键源码；个人职责按实际完成的工作说明。
